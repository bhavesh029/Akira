# Phase 0 — Foundation & Correctness Fixes

**Status:** ✅ Done — build/tests/lint verified, no regressions.
**Testing:** see [`TESTING.md` § Phase 0](../../TESTING.md#phase-0--foundation--correctness-fixes--done--verified).

## Why this phase existed

Before adding reconciliation, RAG, budgets, recurring bills, or net worth, several
existing bugs and missing infrastructure would have undermined all of them: no
migration tooling, a data-type bug on the money column, a timezone bug in every
date-range filter, duplicated filter logic that would need to be triplicated again
for every new feature, a stale-cache bug, and a silent data-loss bug in extraction.
Nothing here is user-visible — it's the ground later phases stand on.

## What was built

### 1. Migration tooling (previously nonexistent)
- `backend/src/data-source.ts` — a standalone TypeORM `DataSource` for CLI use
  (separate from `app.module.ts`'s `TypeOrmModule.forRootAsync`, since the CLI runs
  outside Nest's DI/ConfigModule). `synchronize` is always `false` here.
- `backend/src/migrations/1790767194418-Baseline.ts` — a baseline migration
  generated by diffing an empty database against the current entities, capturing
  the schema `synchronize` had been creating (including `CREATE EXTENSION IF NOT
  EXISTS vector` for the `document_chunks.embedding` column). Verified: applies
  cleanly to an empty DB, reverts cleanly, matches `synchronize`'s output.
- `npm run migration:generate|run|revert` scripts in `backend/package.json`.
- **Decision:** dev keeps `synchronize: true` for iteration speed; migrations are
  required for anything beyond local dev (and for every schema change from Phase 1
  onward).

### 2. `Transaction.amount` decimal transformer
- `backend/src/entities/transformers/decimal.transformer.ts` — a `ValueTransformer`
  that converts Postgres `decimal`/`numeric` strings to real JS numbers on read.
- Applied to `Transaction.amount` in `backend/src/entities/transaction.entity.ts`.
- **Why:** node-postgres returns `decimal` columns as strings by default (to avoid
  silent precision loss) — without a transformer, `amount` was a string at runtime
  despite being typed `number` in TypeScript. Existing analytics code defensively
  wrapped every read in `Number(...)`, but any new code touching the entity
  directly (budgets, net worth, recurring bills) would have inherited the same
  landmine. This transformer will be reused for every new decimal column added
  later (budget limits, account starting balance, document balances).

### 3. Timezone-safe date-range math
- `backend/src/analytics/analytics.service.ts` — replaced local-`Date`-mutation
  logic (`setMonth`/`setDate` on `new Date()`, which depends on the server's local
  timezone) with pure UTC calendar arithmetic (`toIsoDate`, `todayIso`,
  `getStartDateForRange`, `dateRangeFromRelative`), and made every call site bind
  ISO date strings consistently (previously `getSummary`/`getAiInsights` bound raw
  JS `Date` objects as query params, while `financeChat` correctly used strings —
  now everything does).
- **Why:** binding a raw `Date` object as a Postgres query parameter depends on how
  the driver serializes it, which interacts with server timezone in ways that could
  shift "this month" boundaries by hours around midnight IST. UTC-only calendar math
  removes the dependency entirely.

### 4. Shared analytics query filter helper
- Added `AnalyticsService.baseFilteredQuery(userId, accountId?, dateRange?)` —
  the single place `userId`/`accountId`/`dateRange` filters are applied. `getSummary`'s
  main query, its cashflow query (previously a separately-constructed query builder
  that manually re-duplicated the same three filters), and `getAiInsights`'s query
  all now build on this helper.
- Also fixed a stale comment claiming cashflow covers "the last 6 months" — the
  code actually does `.limit(12)` (12 months); comment now matches reality.
- **Why this matters going forward:** Phase 1's `reviewed = true` gate, and every
  later phase that needs "this user's transactions, filtered," add to this one
  method instead of writing a fourth (fifth, sixth...) copy of the same filter
  logic.

### 5. Fixed a stale-cache bug on account deletion
- `backend/src/accounts/accounts.service.ts` — `remove()` now calls
  `aiInsightsCache.invalidateForUser(userId)` after deleting an account (which
  cascades to delete that account's transactions at the DB level).
- Wired `AiInsightsCacheModule` into `AccountsModule` to make this possible.
- **Why:** previously, deleting an account could leave up to 7 days of stale
  AI-generated insights cached, computed from transactions that no longer exist.

### 6. Fixed silent data loss in the extraction fallback
- `backend/src/documents/extraction.service.ts` — the deterministic bank parser
  path now falls back to `geminiService.extractTransactionsFromText(text)` when
  `parserFactory.parseText(text)` either throws (unsupported bank) or returns an
  empty array (a matched-but-stub parser — true today for 5 of the 6 banks).
- **Why:** previously, only "PDF has too little text" triggered a Gemini fallback.
  A statement that matched one of the 5 stub bank parsers (which unconditionally
  `return []`) would silently complete with zero transactions and no error —
  indistinguishable from "this statement genuinely has no transactions."

## Design decisions made here

- **UTC, not user-local-time, as the date-range reference frame.** There's no
  per-user timezone setting in this app, so UTC is the only choice that doesn't
  depend on where the Node process happens to be hosted. Acceptable since
  `transaction_date` is a pure calendar date with no time component.
- **`synchronize` stays on in dev.** Migrations are additive infrastructure for
  safe schema evolution beyond local dev, not a replacement for the fast local
  iteration loop.
- **A `ValueTransformer`, not a decimal/bignum library.** At personal-finance
  scale, `parseFloat` precision is more than sufficient; a full decimal library
  would be over-engineering for this app's actual number ranges.

## Known follow-ups (not blocking, tracked for later phases)

- `Document.error_message` (so `FAILED` documents carry a reason) is deferred to
  Phase 1's migration, since Phase 1 touches `Document`'s schema anyway.

## Test infrastructure added alongside this phase

Before continuing to Phase 1, the following were added as a safety net and to
establish the testing pattern later phases should follow (see
`.agents/rules/build_workflow.md`):

- **Fixed the 5 pre-existing vacuous test scaffolds** (`analytics.service.spec.ts`,
  `analytics.controller.spec.ts`, `auth.service.spec.ts`, `auth.controller.spec.ts`,
  `users.service.spec.ts`) — they previously failed to resolve NestJS DI and only
  asserted `should be defined`. They now provide proper mocked dependencies and
  include real behavioral assertions (e.g. `AuthService` never stores a plaintext
  password; `AnalyticsService.getSummary` correctly separates CREDIT/DEBIT sums).
- **Extracted the pure date-math functions** from `analytics.service.ts` into
  `backend/src/analytics/date-range.util.ts` specifically so they're testable
  without Nest DI or a database, with `date-range.util.spec.ts` covering month/
  leap-year/timezone edge cases (21 tests).
- **`decimal.transformer.spec.ts`** — covers the Phase 0b transformer directly.
- **`extraction.service.spec.ts`** — covers the Phase 0f fallback fix directly
  (parser-returns-empty, parser-throws, short-text-uses-vision, dedup, and the
  document-marked-FAILED-on-error path), using plain constructor-injected mocks
  rather than a full Nest testing module.

Backend test suite went from **5 failing / 1 passing** (pre-existing scaffolds) to
**57 passing across 9 suites**. Run with `cd backend && npm test`.

## Tooling guardrail added alongside this phase

A `PreToolUse` hook (`.claude/settings.json` + `.claude/hooks/check-lint-scope.sh`)
now blocks unscoped `npm run lint` / bare `eslint --fix` invocations for any agent
working in this repo, with a message pointing to the scoped alternative — see
`.agents/rules/build_workflow.md` for why.
